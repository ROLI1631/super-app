# 41. Time Core Specification

## Purpose

This document defines the SO8FI Time Core as the universal operational time standard of the platform. Time Core is not a scheduler, calendar, database, or business module. It is the immutable temporal substrate that every platform event, journal entry, lifecycle transition, and operational decision can rely on.

## Scope

Time Core is responsible for:

- global operational time,
- event ordering,
- event timestamping,
- event lifecycle management,
- time synchronization within the runtime,
- legal event processing,
- operational event processing,
- event expiration and TTL handling,
- archive policy enforcement,
- replay rules,
- snapshot rules,
- recovery and consistency handling,
- time-based validation.

Time Core does not define business semantics, product rules, or domain-specific scheduling logic.

## Core Principles

- One event must have one timestamp.
- One event must create one journal record.
- One event must follow one event route.
- One event must move through one lifecycle.
- Time Core must remain independent from business modules.
- Time Core must preserve ordering and continuity across all platform operations.

## 1. Global Operational Time

Global Operational Time is the platform-wide time reference used by all runtime components. It is expressed as an ISO 8601 timestamp and is the canonical time value stored in journal records and event metadata.

### Rules

- Every accepted event receives one operational timestamp.
- Operational time is generated by the Time Core, not by modules.
- Operational time is stable, monotonic in the context of the runtime, and suitable for ordering and recovery.
- All temporal comparisons use the same operational time source.

### Required Invariants

- A journal entry must carry the same operational time that was used to create the event.
- Time Core must expose a single authoritative clock interface to the platform.

## 2. Event Ordering

Event ordering is the platform’s guarantee that events can be reconstructed in a stable sequence even when processed asynchronously.

### Rules

- Each event receives a monotonic order value.
- The order value is assigned by Time Core and persisted in the event metadata.
- Order values are used for replay, recovery, and consistency validation.
- Ordering must remain independent from business or UI execution order.

### Required Invariants

- Event order must increase strictly with each recorded event.
- The order value must be consistent across journal, replay, and recovery flows.

## 3. Event Timestamping

Event timestamping is the assignment of a canonical time marker to an event at the moment it enters the platform runtime.

### Rules

- Timestamping happens once per event.
- Timestamp values are stored in the journal record and in event metadata.
- Timestamp values are immutable after record creation.
- Timestamp values must be valid ISO 8601 strings.

### Required Invariants

- One event has one timestamp.
- The timestamp is preserved across journal storage, replay, and snapshot operations.

## 4. Event Lifecycle

Every event follows a single lifecycle path managed by Time Core.

### Lifecycle States

- created: the event has been accepted and assigned operational time.
- active: the event is valid and available for processing.
- validated: the event passed time-based validation.
- processed: the event has been routed and consumed.
- expired: the event is no longer valid due to TTL or retention policy.
- archived: the event has been preserved for historical review.

### Rules

- Lifecycle transitions are ordered and explicit.
- Transitions must not be duplicated or skipped in a way that breaks continuity.
- State changes are recorded as part of the operational metadata and journal context.

## 5. Time Synchronization

Time synchronization within the SO8FI runtime ensures that the platform uses a unified operational time notion even when components are executed independently.

### Rules

- The runtime must not rely on independent module clocks.
- Time Core is the only component permitted to assign operational timestamps.
- Synchronization is logical and operational rather than network-based.
- Replay and recovery must reconstruct the same event order and timestamps.

## 6. Legal Event Processing

Legal events are events that carry legal, consent, audit, or governance significance.

### Rules

- Legal events must be timestamped and journaled immediately.
- Legal events must retain their route, lifecycle state, and order value.
- Legal events must not be overwritten or reinterpreted after recording.
- Legal event processing must remain non-business-specific and auditable.

## 7. Operational Event Processing

Operational events are platform-level events that support runtime execution, monitoring, validation, and recovery.

### Rules

- Operational events must follow the same timestamping and lifecycle rules as legal events.
- Operational events must be routed through one canonical event route.
- Operational events are the basis for replay, snapshot, and restoration workflows.

## 8. Event Expiration and TTL

TTL defines how long an event remains active before it becomes expired.

### Rules

- TTL is a platform policy concern and must be evaluated by Time Core or a Time Core-aware runtime component.
- Expiration must be deterministic and based on the event’s operational timestamp.
- Expired events must transition to an expired lifecycle state.
- Expired events remain available for audit and replay unless retention policy removes them.

## 9. Archive Policies

Archive policies govern how historical operational records are preserved.

### Rules

- Archived records must retain their event order and original timestamp.
- Archive policy must preserve the event route and lifecycle context.
- Archived records must never lose their original operational identity.

## 10. Replay Rules

Replay reconstructs platform state using the journal and the assigned temporal order.

### Rules

- Replay must follow the ascending event order.
- Replay must preserve the original timestamp values.
- Replay must restore same route and lifecycle state values.
- Replay must not invent new timestamps or reorder events.

## 11. Snapshot Rules

Snapshots preserve a point-in-time view of the runtime state.

### Rules

- A snapshot must include the last stable operational time and event order.
- Snapshots must be reproducible from journal history.
- Snapshots must be used to recover from restart or state loss.

## 12. Event Recovery

Recovery reconstructs platform state after interruption or data loss.

### Rules

- Recovery must start from the latest valid snapshot.
- Recovery must replay events from the snapshot forward.
- Recovery must preserve the original timestamps and event ordering.
- Recovery must not create duplicate journal records for already recorded events.

## 13. Event Consistency

Consistency ensures that the journal, lifecycle state, and event order remain coherent.

### Rules

- Every journal record must correspond to exactly one event.
- Every event must be recoverable from the journal and snapshots.
- Event order must remain monotonic and non-duplicated.
- Temporal validation must reject inconsistent or malformed timestamps.

## 14. Time-Based Validation

Time-based validation ensures that runtime operations respect temporal rules before they become active.

### Rules

- Invalid timestamps are rejected.
- Events with expired or invalid temporal context are rejected or moved to an expired state.
- Validation must check timestamp format, route continuity, and lifecycle status.

## 15. Runtime Contract

The implementation contract for Time Core is:

- create a canonical timestamp,
- assign a monotonic event order,
- attach operational metadata including operationalTime, eventOrder, eventRoute, and lifecycle,
- persist the event as one journal entry,
- preserve the event for replay, recovery, and validation.

The current runtime implementation now follows this contract by attaching operational metadata to journal entries at record creation time.

## 16. Non-Goals

Time Core does not implement:

- business calendars,
- task scheduling,
- UI timelines,
- marketplace workflows,
- domain business rules.
